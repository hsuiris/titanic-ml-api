# Titanic ML 說明文件

這份文件分兩大部分：

1. **資料分析說明**：白話講清楚這頁的分析做了哪些事、得到什麼結論、你該怎麼看與怎麼用。
2. **程式碼設計說明**：這一頁（以及整個專案）的程式是怎麼架構、資料怎麼流動、每個檔案在做什麼。

這一頁是照著標準的資料科學流程設計的：Business Problem → EDA → Data Cleaning → Feature Engineering → Train/Validation Split → Baseline → 比較多模型 → Hyperparameter Tuning → Cross Validation → Feature Importance → Final Model → Predict → Deployment。頁面最上方有一張「分析流程」時間軸把這些步驟串起來。

# 第一部分：資料分析說明（白話版）

一句話總結：**我們把 891 位乘客的資料整理乾淨、做出更有用的新特徵，讓電腦從中學會「什麼樣的人比較容易生還」，再拿它來預測新的人。**

## 一、我們怎麼整理資料（前處理 + 特徵工程）

原始資料沒辦法直接餵給模型，所以先做了這些事：

- **補缺值**：年齡有 177 人沒填、登船港有 2 人沒填。年齡用「中位數」補、登船港用「最常見的港口」補，不亂猜，用整體的常態值。
- **把文字變成數字**：模型只看得懂數字，所以性別、艙等、登船港、稱謂這類「類別」，用 One-Hot 拆成一堆 0/1 欄位。
- **把數字拉到同一尺度**：年齡是 0 到 80、票價可到好幾百，差太多會讓某些模型偏心，所以做了標準化（StandardScaler）。
- **特徵工程（這步最關鍵）**：從原始欄位做出更有用的新特徵。
  - **Title（稱謂）**：從姓名（例如「Braund, Mr. Owen Harris」）抽出 Mr / Mrs / Miss / Master，其他罕見稱謂歸為 Rare。Title 同時藏了性別、年齡、社會地位的訊息，是很強的特徵。
  - **FamilySize（家庭人數）**：把 SibSp（手足配偶）+ Parch（父母子女）+ 1 加起來。
  - **IsAlone（是否獨自一人）**：家庭人數等於 1 就是獨自搭船。
  - 消融對照（同一最佳模型、有無特徵工程）：SVM 的測試準確率從 79.3%（12 個輸入欄位）提升到 84.4%（18 個輸入欄位），約 +5 個百分點。
- **最後進模型的欄位**：Age、Fare、FamilySize（數值），以及 Pclass、Sex、Embarked、Title、IsAlone（類別）。丟掉姓名原文、船票號碼、船艙，因為它們幾乎人人不同或大量缺漏（船艙缺 687 筆）。
- **分訓練 / 測試**：8 成拿來學、2 成藏起來當考題（分層抽樣，固定亂數種子）。這樣分數才誠實，不是自己出題自己考。

## 二、我們發現了什麼（結論）

資料很誠實地說出了那個年代的殘酷邏輯：

- **性別最關鍵**：女性生還率 74%，男性只有 19%，差了快 4 倍。「婦女優先上救生艇」在數字上一清二楚。
- **艙等其次**：頭等艙 63%、三等艙只有 24%。艙位不只是價錢，某種程度也決定了離救生艇的距離與機會。
- **稱謂與年齡也有影響**：Master（小男孩）的生還率偏高，呼應「孩童優先」。這也是為什麼 Title 這個特徵這麼有用。
- 「特徵重要度」那張圖講的是同一個故事：**Title、性別、FamilySize** 都排在很前面。

## 三、模型怎麼挑、到底準不準

我們沒有只賭一個模型，而是同時訓練五種，每種都自動試很多組參數（GridSearch），再挑最好的：

- **Logistic Regression（baseline）**：先用最簡單的模型建立比較基準，準確率約 83.8%。
- 再比較 **Decision Tree、Random Forest、SVM、XGBoost**。
- 最後 **SVM（線性核）勝出，準確率約 84.4%**（在它沒看過的測試資料上），比 baseline 再好一點。訓練時會另外對最佳模型做一次「無特徵工程」的消融對照。
- **ROC-AUC 0.86** 的白話意思：隨便抓一個真生還、一個真罹難的人，模型有 86% 機率會把生還者評得分數比較高。越接近 1 越強，0.5 等於瞎猜。
- 混淆矩陣看得出它錯在哪：偶爾把該活的判成沒活（漏判）、把沒活的判成活（誤判），這在真實模型很正常。

## 四、預測結果怎麼看、怎麼用

- 「單筆預測」給你的是**一個生存機率，不是鐵口直斷**。60% 代表「以歷史來看，這種條件的人大約六成活下來」。
- 我們用 **0.5 當門檻**：超過標「生還」、低於標「未生還」。你心裡可以自己調，例如很在意「別漏掉會死的人」，門檻就該放低一點。
- 「批次預測」適合一次跑很多人：上傳一份 CSV，它會逐列附上生還判斷與機率，還能下載回去。CSV 只要有姓名（或直接給 Title）等欄位，就能自動算出稱謂特徵。

## 五、要記得的事（別過度解讀）

> 這是一份**歷史資料的統計規律，不是命運判決**。模型說的是「這類人過去的生還比例」，不是「這個人一定會怎樣」。而且相關不等於因果，不是「因為是女生所以會活」，而是當年的制度讓女性有較高機會。拿來練資料分析很好，別拿它對真人下結論。

# 第二部分：程式碼設計說明

## 1. 專案長什麼樣子

```
titanic/                          # 專案根目錄（獨立在 GitHub 資料夾）
├─ models/                        # 訓練後才會出現：存下來的最佳模型與中繼資料
│  ├─ titanic_model.joblib        #   最佳模型（含前處理的完整 Pipeline）
│  ├─ meta.json                   #   這次訓練的完整結果（比較表、指標、超參數）
│  └─ history.json                #   歷次訓練紀錄
├─ titanic_restful_project/       # 網站主程式
│  ├─ app.py                      #   Flask：路由層（頁面 + REST API），只做轉發
│  ├─ ml.py                       #   機器學習核心：前處理 / 訓練 / 評估 / 預測
│  ├─ init_db.py                  #   把 titanic.csv 匯入 SQLite
│  ├─ my_db.db                    #   SQLite 資料庫（titanic 資料表，891 筆）
│  ├─ titanic.csv                 #   原始資料
│  ├─ requirements.txt
│  ├─ templates/                  #   前端頁面（index / new / edit / ml）
│  ├─ static/app.css              #   共用設計系統
│  └─ doc/                        #   說明文件.md、講稿.md、images/
└─ README.md
```

**一句話設計原則**：`app.py` 是「服務生」，只負責接單、把單子轉給廚房；`ml.py` 是「廚房」，真正在做菜。兩者分開，web 層才乾淨、ML 邏輯才能單獨測試。

## 2. 資料怎麼流動（整體架構）

```
   瀏覽器 (ml.html + 原生 JS)
        │  fetch() 打 REST API
        ▼
   app.py  (Flask 路由層)
        │  呼叫函式
        ▼
   ml.py  (scikit-learn)
        ├── 讀資料 ──►  my_db.db (SQLite)
        └── 存/載模型 ─►  model/*.joblib + *.json
```

前端完全不碰資料庫或模型，只透過 API 拿 JSON；後端完全不管畫面，只回資料。這就是 **RESTful + AJAX** 的分工。

## 3. 後端：`ml.py` 的設計重點

### (a) 特徵工程 + 前處理都用 Pipeline 包起來（訓練與預測共用同一套）

`_engineer()` 先做特徵工程（Title / FamilySize / IsAlone），接著用 scikit-learn 的 `Pipeline` + `ColumnTransformer` 把補值、編碼和模型綁在一起：

```
_engineer()：Name → Title、SibSp+Parch → FamilySize、衍生 IsAlone
        ▼
ColumnTransformer
├─ 數值欄 [Age, Fare, FamilySize]              → 中位數補值 → 標準化
└─ 類別欄 [Pclass, Sex, Embarked, Title, IsAlone] → 眾數補值 → One-Hot
        ▼
分類器 (LogReg / DecisionTree / RF / SVM / XGBoost)
```

存檔時是把「特徵工程以外的前處理 + 模型」整個 Pipeline 一起用 `joblib` 存起來，預測時丟原始欄位進去就好，同樣的處理會自動跑一遍。**一次定義，訓練與預測都用同一套，不會不一致。**

> 有兩個容易踩的雷已先處理掉：
>
> 1. `Pclass` 在資料庫是整數 1/2/3，但表單送來可能是字串 "3"。One-Hot 會把 `int 1` 和 `str '1'` 當成不同類別而對不上，所以 `_prep_frame()` 統一把類別欄轉成字串。
> 2. Title 在「訓練 / 批次」是從 Name 抽出來的；但「單筆預測」表單沒有姓名，所以改成直接給一個 Title 下拉選單。`_engineer()` 兩種情況都相容。

### (b) 一鍵訓練 = baseline + 多模型 + 自動調參 + 自動選最佳

`_train()` 的流程：

1. 從 SQLite 撈全部資料，做特徵工程，分層切成訓練 / 測試（8:2，`random_state=42` 固定，結果可重現）。
2. 對五種模型各跑一次 `GridSearchCV(cv=5)`（Logistic Regression 當 baseline，另外四個是 Decision Tree、Random Forest、SVM、XGBoost）。這就是「自動調超參數」：把 grid 裡每組參數都用 5 折交叉驗證試一遍，挑分數最高的那組。
3. 每個模型在**測試集**上算：準確率 / Precision / Recall / F1 / ROC-AUC + 混淆矩陣 + ROC 曲線點。
4. 用準確率挑出最佳模型，`joblib.dump()` 存檔，並把完整結果寫進 `meta.json`、追加一筆到 `history.json`。

> Boosting 這一類用 XGBoost（`xgboost` 套件），是實務上常拿來打比賽的梯度提升模型；其餘皆為 scikit-learn。

### (c) 訓練狀態：背景執行緒 + 輪詢

訓練要幾秒鐘，如果讓 API 卡著等，畫面會凍住。所以：

- `start_training()` 開一條背景 thread 跑 `_train()`，馬上回傳「開始訓練」。
- 訓練過程把進度寫進一個 module 級的 `_status` 字典（用 `Lock` 保護，避免多執行緒打架）。
- 前端每 1.2 秒打一次 `/api/train/status` 問進度，看到 `done` 就把結果畫出來。

這就是為什麼頁面「看得到訓練中，接著變完成」而不會卡死。

### (d) 模型是有狀態的、可持久化

模型存成檔案（joblib + meta.json），所以：**重整頁面、甚至重開伺服器，模型都還在**。頁面載入時打 `/api/model/info` 讀 `meta.json` 還原狀態。`_load_model()` 還會比對檔案修改時間做快取，重訓後自動換成新模型。

## 4. 後端：`app.py` 的路由

`app.py` 只有薄薄一層，把 HTTP 請求轉給 `ml.py`：

| 方法 | 路徑                   | 做什麼                                  |
| ---- | ---------------------- | --------------------------------------- |
| GET  | `/ml`                | 回機器學習頁面                          |
| GET  | `/api/stats`         | 資料概覽（生還率、年齡分布）給上方圖表  |
| POST | `/api/train`         | 開背景訓練                              |
| GET  | `/api/train/status`  | 查訓練進度                              |
| GET  | `/api/model/info`    | 目前存檔模型的完整資訊                  |
| GET  | `/api/history`       | 訓練歷史                                |
| POST | `/api/predict`       | 單筆預測，回`{survived, probability}` |
| POST | `/api/predict/batch` | 上傳 CSV 批次預測                       |

（另外還有原本的 `/api/passengers` CRUD 一組，給資料管理頁用。）

> 批次預測有個細節：缺值在 pandas 是 `NaN`，但 `NaN` 不是合法 JSON，瀏覽器 `response.json()` 會解析失敗。所以在回傳前先把 `NaN` 轉成 `null`。

## 5. 前端：`ml.html` 的設計

### (a) 分析流程時間軸

整頁是以機器學習 Pipeline 為主軸的儀表板：左側是固定的流程導覽（資料概覽 → 前處理 → 特徵工程 → 模型訓練 → 超參數調校 → 模型評估 → 特徵重要度 → 預測），右側每個節點都放該階段完整的分析結果（圖表、統計、比較表、參數與耗時），使用者可以沿著流程一路看下來，不用在區塊間跳來跳去。捲動時左側會自動高亮目前所在的步驟（IntersectionObserver 做的 scrollspy）。版面用寬版 Responsive Layout，桌面充分利用左右空間，視窗變窄時自動收合成單欄。

### (b) 原生 JavaScript + fetch，不用框架

整頁沒有 React/Vue，就是原生 JS：`fetch()` 拿 JSON，用樣板字串組 HTML 再塞進去。夠簡單、看得懂、也沒有打包工具的負擔。

主要幾個函式：

- `loadStats()`：畫資料概覽（大數字、長條圖、直方圖）。
- `startTrain()` / `pollStatus()`：觸發訓練 + 輪詢進度。
- `renderModel()`：畫比較表（標出 baseline 與最佳）、混淆矩陣、ROC、特徵重要度。
- `predictOne()` / `predictBatch()`：單筆（含 Title 下拉）/ 批次預測。
- `runTune()`：互動式超參數試跑，讓使用者自訂 Random Forest 搜尋範圍即時重跑（不覆蓋已存檔模型）。
- `calcScale()` / `toggleReveal()`：前處理步驟的即時標準化計算機與程式碼展開。

### (c) 圖表零外部依賴（純 SVG / CSS）

沒有引用 Chart.js 之類的套件，所有圖表都是自己刻的，好處是**離線也能跑、作品集展示不怕斷網**：

- **長條圖 / 直方圖**：用 CSS 設定 `div` 的寬 / 高。
- **ROC 曲線、生存機率儀表**：用 inline SVG（`stroke-dasharray` 畫圓弧、`polyline` 畫曲線）。
- **混淆矩陣**：2×2 的上色格子。

圖表配色（teal + ochre）有先用色彩對比與色盲檢測驗證過，確保看得清楚。

### (d) 共用設計系統：`static/app.css`

4 個頁面共用同一份 CSS，所有顏色、圓角、陰影都寫成 CSS 變數（`:root` 的 `--hero-a`、`--chart-blue` 等）。**要改主題只改一個檔**，全站同步。深藍 hero、白卡片、藥丸按鈕、生還/未生還色碼都定義在這裡。

## 6. 怎麼跑起來 / 怎麼驗證

```bash
# 1) 如果還沒有資料庫，先建：
python init_db.py

# 2) 啟動網站：
python app.py            # 開 http://127.0.0.1:5000/ml

# 3) 單獨測 ML 核心（會實際訓練一次並自我檢查）：
python ml.py
```

`ml.py` 的 `__main__` 附了自我測試：訓練，確認有 5 個模型結果與最佳模型，預測一筆，檢查機率落在 0 到 1，確認歷史有寫入。跑得過就代表核心邏輯正常。

## 7. 幾個「為什麼這樣設計」的取捨

- **ML 和 web 分開**：`ml.py` 可以單獨 import、單獨測試，不依賴 Flask。
- **背景 thread 而非同步等待**：滿足「看得到訓練狀態」的需求，訓練久也不卡畫面。
- **固定亂數種子**：每次訓練結果一致，方便對照與展示。
- **模型持久化**：重開也不用重訓，符合真實服務的做法。
